# 404, not 403, for data outside the requester's set

## Context and Problem Statement

An account asks for data that belongs to another account. The response was
written as 403 in a table that predates several later decisions, among them the
owner filter of ADR 0005 — which is what produces a 404, because the object is
not in the set already filtered by the requesting account.

## Considered Options

* **403**, the code the earlier table wrote.
* **404**, the code Django REST Framework produces on its own once the query is
  filtered before it runs.

## Decision Outcome

Chosen option: **404**, where the framework produces it naturally. No code is
written to force a 403 there.

404 is the stronger answer, not the weaker one. 403 says *it exists and is not
yours*, and reveals that the data exists; 404 reveals nothing. It is the same
choice already made for an invitation sent to an address the system cannot
find, which answers the same thing either way (`docs/api-behaviour.md`).

403 does not disappear. It stays where it is true: the object is visible and
what is refused is the action.

The response for each situation is `docs/api-behaviour.md`.
